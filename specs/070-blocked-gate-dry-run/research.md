# Phase 0 Research: A never-unblocking merge gate is named

Input: `spec.md`, fully clarified (all three questions on lifecycle issue
#533 answered in the Clarifications session; no `[NEEDS CLARIFICATION]`
markers remain in scope — Q2 and Q3 dropped the pause-switch/release-free
dispatch work entirely, leaving only Q1's 20-minute allowance, which the
spec already folds into FR-004). This phase resolves *technical* unknowns —
how to distinguish and time the empty-rollup blocked state inside the
existing `verify-e2e` job — not what to decide.

Each entry is a Decision / Rationale / Alternatives triad, per the plan
template's format. File:line citations are against `auto-release.yml` and
related files as of `0c12ced` (the branch head this plan starts from).

## D1. A new decision-script token distinguishes "blocked, nothing resolved" from every other `wait` (FR-001, FR-002)

**Decision**: `auto-release-e2e-merge-decision.sh`'s existing step 6 (`.github/actions/_shared/auto-release-e2e-merge-decision.sh:76-122`, contract `specs/055-unattended-e2e-gates/contracts/gate-decision-scripts.md` step 6) currently prints `wait` whenever `mergeStateStatus == "BLOCKED"` and the rollup has nothing resolved yet (empty array, or every entry still pending/`EXPECTED`, in either the CheckRun or legacy StatusContext shape). This plan changes that one branch to print a new token, `blocked-pending`, instead. Every other `wait`-producing branch — `isDraft` (step 4), `UNKNOWN`/`BEHIND` `mergeStateStatus` (step 7) — keeps printing `wait` unchanged, because those conditions are not what FR-001/FR-002 are about: a draft PR or a `mergeStateStatus` GitHub is still computing is not "required checks never reported," and timing them against the new allowance would risk stalling attempts FR-002 explicitly says must not be declared stalled.

**Rationale**: FR-001 requires distinguishing "waiting on required checks that have not reported" from "the pipeline under test merely taking a long time." The only place that distinction can be made accurately is exactly where the rollup is already being inspected (this script), because that is the one place the CheckRun-vs-legacy-StatusContext shape branching and the empty-rollup special case (both maintainer-feedback fixes from PR #389) already live — duplicating that inspection anywhere else in the `poll` step's own bash would re-derive judgment CLAUDE.md's single-home rule and Constitution IX both argue against.

**Alternatives considered**: Keep printing `wait` and have the `poll` step re-inspect `statusCheckRollup` itself to decide whether to start the allowance timer — rejected: that is exactly the "shared logic has exactly one home" violation CLAUDE.md warns about, would need to re-implement the CheckRun/StatusContext branching a second time, and the two copies could drift the same way the containment-verdict bug this repo has already hit once did. Reuse the existing `blocked` token — rejected: `blocked` already means "durably blocked, a required check resolved and failed" (`write_verdict ... "PR #${pr_number}: required check blocked"`, `auto-release.yml:1014-1017`) and is treated as an immediate stall with no waiting allowance at all; collapsing the two would either stall a check that is still merely pending (breaking FR-002/Acceptance Scenario 3) or stop treating a resolved-and-failed check as an immediate stall (breaking existing coverage). A more descriptive multi-word token (`wait-checks-pending`, `blocked-nothing-resolved`) — rejected in favor of `blocked-pending`, which is shorter, reads clearly next to the existing single-word vocabulary (`none`/`wait`/`blocked`/`conflicting`/`merge`), and pairs naturally with `blocked` as "the softer, still-timing-out sibling."

## D2. A second pure script owns the allowance judgment, not inline `poll`-step bash (FR-002, FR-004, FR-005)

**Decision**: add `.github/actions/_shared/auto-release-e2e-gate-allowance-decision.sh`, a new pure script with the same shape and invocation idiom as the merge-decision script (no network calls, stdin/argv in, one word (+ optional payload) out). It takes the merge-decision token just printed for this gate, this gate's own `blocked_since` marker (empty string if not currently timed), the loop's current `$SECONDS`, and the allowance in seconds, and prints exactly one of:
- `clear` — the merge decision this iteration was not `blocked-pending`; the caller resets `blocked_since` to empty (FR-005: reset on leaving the blocked-with-unresolved-checks state).
- `start` — the merge decision is `blocked-pending` and `blocked_since` was empty (first such observation this attempt); the caller records `blocked_since = $SECONDS`.
- `wait` — the merge decision is `blocked-pending`, `blocked_since` is set, and elapsed time is under the allowance; the caller keeps polling, `blocked_since` unchanged.
- `stall` — the merge decision is `blocked-pending`, `blocked_since` is set, and elapsed time has reached the allowance; the caller writes the new `fail-gate-stall` verdict.

**Rationale**: this is the same judgment/state split research.md D5/D6 already established for spec 055's two decision scripts — "the fetch (network) stays in the `poll` step... the decision (judgment) moves into these scripts, per Constitution IX and Principle VIII's local-testability requirement" (`contracts/gate-decision-scripts.md:5-7`). The allowance arithmetic is a judgment gating a durable action (a `fail-gate-stall` verdict write) exactly as Constitution IX describes, and a pure script taking synthetic `blocked_since`/`$SECONDS`/allowance values as arguments is trivially fixture-testable with no real waiting and no mocked `gh` calls — the same reason the merge-decision script itself is a script and not inline bash.

**Alternatives considered**: Inline `if [ -z "${gate_blocked_since[$prefix]}" ]; then ...` arithmetic directly in the `poll` step, the way `gate_failures`/`MAX_GATE_FAILURES` is handled today (`auto-release.yml:985-1038`) — rejected even though it would work and would be short, because the existing failure-counter bookkeeping is pure "count and compare an integer," never mistaken for a rollup-shape judgment, whereas this timer's *reset* rule (FR-005: reset only on leaving the blocked-with-unresolved-checks state, never on the rollup's shape merely changing) is exactly the kind of edge-case-laden judgment Constitution IX asks to be pushed into fixture-testable code rather than trusted to be re-derived correctly by eye during implementation or a later edit. Folding the allowance directly into the merge-decision script (having it also take `blocked_since`/`$SECONDS`/allowance as extra arguments and decide `wait-blocked`/`stall` itself) — rejected: it would mix "what does this snapshot of the PR mean" (a pure function of `PR_LIST_JSON` alone today) with "how long has that meaning persisted" (a function of caller-held state across iterations), widening that script's contract for every one of its five call-site-independent scenarios even though only one branch needs timing; two small single-purpose scripts stay easier to fixture independently and to read against FR-001 (naming) versus FR-004/FR-005 (timing) separately.

## D3. Timer state shape: a third associative array parallel to `gate_failures` (FR-005)

**Decision**: add `declare -A gate_blocked_since=([spec-draft/]="" [plan/]="" [spec/]="")` beside the existing `gate_merged`/`gate_name`/`gate_failures`/`gate_last_failure` declarations (`auto-release.yml:866-869`), keyed by the same `prefix` values. After each gate's merge-decision call succeeds, the loop calls the new allowance-decision script with `${gate_blocked_since[$prefix]}` and `$SECONDS`, and applies its answer: `clear` empties the entry, `start` sets it to `$SECONDS`, `wait` leaves it untouched, `stall` triggers the new verdict write (using the existing `gate_name`/`write_verdict`/`emit_verdict`/`exit 0` idiom every other stall reason already uses at this same site).

**Rationale**: matches the existing precedent exactly (three parallel per-gate associative arrays already exist; a fourth is the smallest change that fits the established shape) and keeps the timer's clock the same `$SECONDS` the outer `while` loop and `POLL_BUDGET_SECONDS` already use, so no new time source or format is introduced.

**Alternatives considered**: a single associative array of small records (JSON per gate) — rejected as unnecessary complexity for three independent scalar values that already have three independent arrays to sit beside. Wall-clock timestamps (`date +%s`) instead of `$SECONDS` — rejected: `$SECONDS` is already the loop's authoritative elapsed-time source (`POLL_BUDGET_SECONDS` comparison at line 893), and introducing a second clock would risk the two drifting under a suspended/throttled runner in a way a single shared clock cannot.

## D4. Verdict text for the new stall reason (FR-003)

**Decision**: the `stall` branch calls `write_verdict "fail-gate-stall" "${gate_name[$prefix]}" "gh pr merge succeeds" "PR #${pr_number}: required checks never reported a result"` — same `gate_name` map, same `"gh pr merge succeeds"` expectation string every other merge-gate stall reason already uses (`conflicting`, `blocked`, `wrong-attempt`, `wrong-base` at `auto-release.yml:1010-1027`), differing only in the `observed` text.

**Rationale**: FR-003 requires naming the gate "using the same gate names the existing gate-stall reasons use" and stating "its required checks never reported a result" — this is a direct restatement of that requirement into the existing call shape, adding no new verdict field (data-model.md) and reusing the report job's existing `fail-gate-stall` → "gate stall" classification (`auto-release.yml:1790-1794`) unchanged, exactly as `contracts/verdict-extension.md`'s existing table already does for the four prior reasons.

**Alternatives considered**: a distinct `outcome` value for this reason (e.g. `fail-gate-timeout`) — rejected outright by the spec's own Assumptions ("the existing verdict vocabulary is sufficient... adds a new *reason* within the existing gate-stall outcome rather than a new outcome").

## D5. Fixture strategy: extend Gate 66 and Gate 52, register nothing new (FR-009, Constitution VIII)

**Decision**:
- Gate 66 (`.github/scripts/verify-auto-release-e2e-gate-decisions.py`): (a) the three existing `MERGE_SCENARIOS` entries for "BLOCKED, no pending check registered yet," "a check still running," and both legacy-StatusContext-pending variants (lines 269-293 as of this branch) have their `expect_head` changed from `"wait"` to `"blocked-pending"`, since D1 renames exactly that branch — this is a call-site update, not new coverage, and its corresponding `MERGE_MUTATIONS` entries (the `still_pending`/empty-rollup/StatusContext mutations) are updated to assert against the new token so a regression that collapses `blocked-pending` back into `wait` still fails the mutation check. (b) A new `ALLOWANCE_SCENARIOS` list + `run_allowance_suite()`, mirroring `MERGE_SCENARIOS`/`run_merge_suite()`, exercises the new allowance-decision script's four branches directly against synthetic `blocked_since`/`now`/allowance triples — no real waiting, no mocked `gh` — covering FR-009's five required branches: `blocked-pending`, no prior `blocked_since` → `start` (branch: first observation); `blocked-pending`, elapsed under allowance → `wait` (branch: inside the allowance); elapsed at/over allowance → `stall` (branch: allowance exhausted); a non-`blocked-pending` decision (e.g. `merge`, or `wait` from a draft/UNKNOWN/BEHIND PR) with a previously-set `blocked_since` → `clear` (branches: "resolves to a pass inside the allowance" and "reset by observable progress," both exercised as the caller applying `clear`). A matching `ALLOWANCE_MUTATIONS` list breaks each of the four branches once, proving the fixture would catch a regression in each (Constitution VIII).
- Gate 52 (`.github/scripts/verify-auto-release-report.py`): one new `GATE_STALL_*` fixture built with the existing `gate_stall(failing_check, expected, observed)` helper (`verify-auto-release-report.py:119-123`), using D4's exact strings, added alongside `GATE_STALL_SPEC_DRAFT`/`GATE_STALL_PLAN`/`GATE_STALL_FINALIZE` (`verify-auto-release-report.py:126-136`) and wired into the same `body_contains`/`body_excludes` assertion pattern the other three already use (around lines 444-469) — proving the rendering and "gate stall" classification, already generic over the `observed` string, need no code change for the new reason.
- FR-009's fifth required branch, "the unchanged generic timeout," is proven by (i) the `ALLOWANCE_SCENARIOS` case above where a non-`blocked-pending` `wait` (e.g. a draft PR held indefinitely) always resolves to `clear`, never `stall` — demonstrating the new logic cannot turn an unrelated `wait` into a stall — and (ii) leaving `auto-release.yml` lines 1083-1089 (the generic-timeout write) and lines 1790-1794 (the classification `case`) completely unedited, which the tasks stage's diff itself is the evidence for, since no fixture existed for that branch before this feature and inventing a new one is out of scope (nothing about the generic-timeout branch changes).

**Rationale**: CLAUDE.md: "shared logic has exactly one home" — both decision surfaces already have exactly one fixture home (Gate 66 for pure decision-script branches, Gate 52 for verdict-to-classification rendering), established by spec 055; this feature's new branches are additions to those same two homes, not a third gate. Constitution VIII requires every shipped failure branch be exercised by a checked-in fixture reachable through the gate registry and requires a gate be triggered by changes to the tree it checks — both gates already run on changes to their respective `.sh`/`.py` files via `lint-workflows.yml`'s existing path triggers, so no trigger change is needed.

**Alternatives considered**: a new `verify-auto-release-e2e-gate-allowance.py` gate dedicated to the new script — rejected: it is the same decision-script fixture pattern Gate 66 already implements (stdin JSON/args in, stdout token out, mutation self-test), and a second near-identical harness is exactly the kind of pasted-copy CLAUDE.md's "shared logic has exactly one home" section warns against, this time at the harness level rather than the shell level. Testing the timer via a real multi-iteration run of the `poll` step's bash with mocked `gh` and manipulated `$SECONDS` — rejected: no existing harness drives that step's stateful loop at all (only `wc_shell_harness.run_step`, used by Gate 52, executes a single non-looping step), and building one to advance a live `$SECONDS` clock through a 30-second-`sleep`-driven loop is far more machinery than the arithmetic being tested warrants; extracting the judgment into its own pure script (D2) is what makes that heavier harness unnecessary.
